### T-025：三个 no-op 分支接上了真实语义

**问题比台账说的更重。** 旧代码三个 `match` 分支全是 `opts`（no-op），
更关键的是 `VerifyFull` 分支的注释写着「留 opts 默认」——
而 **sqlx 的默认是 `Preferred`，根本不校验证书**。
也就是说：代码宣称「默认强制校验 CA + 主机名」，实际**一次都没校验过**。

**映射（语义逐条对齐 sqlx 0.8.6 的真实实现）**：

| 应用侧档位 | MySQL | PostgreSQL | 语义 |
|---|---|---|---|
| `verify_full`（默认） | `VerifyIdentity` | `VerifyFull` | **验 CA + 验主机名** |
| `prefer` | `Required` | `Require` | 加密但**不校验证书**（降级，打警告） |
| `disable` | `Disabled` | `Disable` | 明文 |

> 依据 sqlx 源码实测（`sqlx-mysql-0.8.6/src/connection/tls.rs:64`）：
> `accept_invalid_hostnames: !matches!(ssl_mode, VerifyIdentity)` ——
> 只有 `VerifyIdentity` 才验主机名；`Required` 走 `accept_invalid_certs=true`（加密但不校验）。

**顺带补上的两件东西**：

1. **私有 CA 通道**：本仓 sqlx 的 feature 是 `tls-rustls`（= `webpki_roots` 内置
   Mozilla 公共 CA 集，**不是**操作系统钥匙串里的系统根）。企业自签 CA 必须显式给文件，
   否则 `verify_full` 连不上且用户无路可走。已加 `ssl_ca` / `ssl_root_cert`。
2. **用户可选**：新增 `tls_mode` / `tls_ca_path` 两个配置字段（`DBConfig` 与
   `ConnectionRecord` 都有，落盘能留住），前端连接表单给出下拉 + CA 路径输入框。
   优先级：**连接配置 > 环境变量 > 默认（最安全的一档）**。

### 为什么这件事值得单独做一轮

骨架 API 的危险之处在于：**它能编译、测试也能调，但生产路径上从没被走到过**。
于是它的行为是**未定义的**，而界面照样显示"成功"。

本轮查实的三条实证（都是"界面说成功、事实不是"）：

1. **"事务"只是本工具侧记账**。普通连接池有多条连接 ⇒ `BEGIN` 与 `COMMIT` 落到
   **不同连接** ⇒ 数据库端根本没有这个事务。SQLite 报 `no transaction is active`；
   MySQL 更糟 —— 悄悄提交了一个空事务，而界面显示"事务已提交"。
   （`mod tests` 里那条 `transaction_tracking_updates_registry` 只断言**注册表**状态，
   查不到数据库这一层 ⇒ 一直绿。）
2. **多语句 SQL 能过只读/审批门禁**。`SELECT 1; DROP TABLE x` 的第一条是安全 SELECT，
   而审批与只读判据都只看第一条 ⇒ 等于留了个删表的后门。
   叠加 `classify` 的多语句计数**少算一条**（结尾没分号时算成 0）——
   仓里 `ai_sql.rs` 早就绕开这个坑自己数了，安全门禁却用了错的那个。
3. **`execute_batch` 在可写模式下完全不查审批**。它只判了 `access_mode` 就直接执行。

### 逐项接线（每条都配了回归用例）

### 顺带修掉的另外三个真问题

- **SQLite `:memory:` 的池连接数必须为 1** —— 每条连接就是一个独立的库，
  原来"建表"和"查询"可能落在不同的库上（`no such table`）。
  （`report/source.rs` 里那条 `in_memory_sqlite_skips_path_check_but_shares_nothing`
  断言的正是"每次都是空库"这个**限制**；限制没了，断言也跟着改成"能读到了"。）
- **端口 0 的校验挪到按驱动的地方** —— 反序列化层不知道驱动，而 SQLite 压根没有端口
  （前端就送 0）⇒ 原来**任何 SQLite 连接都存不进去**（`de_port` 直接拒 0）；
  现在放行 0，MySQL/PG 在建池那一刻拒。
- **测试的共享目录锁从 `std::sync::Mutex` 换成 `tokio::sync::Mutex`** ——
  16 处 `await_holding_lock` 落在它身上；`current_thread` runtime 下持 std 锁跨 await
  是**真死锁风险**。

### 门禁挂上之后：CI 第一次就红了（本轮最值钱的一条教训）

commit `96063d2` 推上去后，CI run `39653200063` 在**新挂的** `Clippy (deny warnings)` 步红了
（前面 11 步全绿，含 315 条 Rust 测试）⇒ **门禁一挂上就抓到东西了**，这正是它的价值。

取 CI 日志（`GET /actions/jobs/<job_id>/logs`）定位到唯一一条错误：

```
error: approximate value of `f{32, 64}::consts::GOLDEN_RATIO` found
    --> src/report/expr.rs:1231:32
1231 |             ("f", Value::Float(1.61803)),
```

**根因是版本差，不是这轮新写的代码**：

| | clippy 版本 | `approx_constant` 认不认 `GOLDEN_RATIO` |
|---|---|---|
| 本机（Homebrew rust 1.98） | 0.1.98 | **不认** ⇒ 本地 0 条告警 |
| CI（`dtolnay/rust-toolchain@stable`，当日 stable） | **1.99.0** | 认 ⇒ 红 |

⇒ **「本机 clippy 绿」不等于「CI clippy 绿」**。本地量不到时，量具（clippy 版本）本身就是变量。

**修法是修真 lint，不是回退门禁**：改用标准库常量 `std::f64::consts::GOLDEN_RATIO`
（clippy 自己给的修法），从根上消掉「近似值」这件事，而不是加 `#[allow]` 把它糊过去。
断言 `ROUND(f, 2) == 1.62` 仍精确成立 —— `ROUND` 的实现是 `floor(v*p + 0.5)/p`，
`162.0/100.0` 与字面量 `1.62` 是同一个 double。

**⚠️「CI 报了 1 条」不等于「只有 1 条」**：CI 那次编译在 lib-test 就中止了 ⇒
**集成测试目标根本没被 lint**。所以那条「只有一处」的结论是**补扫**出来的：
把整仓 **126 处浮点字面量**对标准库 **17 个常量**（`PI`/`TAU`/`E`/`SQRT_2`/`LN_2`/`LN_10`/
`FRAC_PI_*`/`GOLDEN_RATIO`/…）逐个算距离，只有 `1.61803` 贴近常量（距离 **3.99e-06**），
其余最近的距离都 **> 1e-3**。

**本机复现 CI 的 lint 集（不用等 CI 往返）**：本机有 rustup 且能连 rust-lang.org ⇒
`rustup toolchain install 1.99.0 --profile minimal --component clippy --component rustfmt`
之后用 `cargo +1.99.0 clippy` 跑，**和 CI 同版本**：

| 验证项 | 1.99.0 结果 |
|---|---|
| `cargo +1.99.0 clippy --locked --all-targets -- -D warnings` | **rc=0，0 条** |
| `cargo +1.99.0 test --locked --all-targets` | **315 passed / 0 failed / 2 ignored** |
| `cargo fmt --all --check` | rc=0 |

**反向钉（证明这条判据咬得住）**：把 `GOLDEN_RATIO` 改回手写的 `1.61803` ⇒
`cargo +1.99.0 clippy` **rc=101** 并逐字报 `approximate value of f{32, 64}::consts::GOLDEN_RATIO found`
⇒ 探针的「咬得住」是**先证过**的，不是假设的。改回常量后 rc=0。

**残留（如实记账）**：CI 用的是**浮动 `stable`** ⇒ 上游 clippy 一旦新增 lint，
门禁会在**零代码改动**下变红。处置约定：**见到零改动红 = 上游 lint 新增 ⇒ 修真 lint，
不回退门禁、也不回退成浮动容忍**。

### 先量：后端做了、界面没入口的有多少？

写了一把**新尺子**（`tests/ipcContract.test.ts`），把前后端命令面拉平对比：

| 方向 | 数量 | 含义 |
|---|---|---|
| 前端调了、后端没注册 | 0 | 点了必崩 |
| 后端注册了、前端从不调 | **16** | 功能做了，界面没有 ⇒ 等于没有 |
| 前端传了、后端不认的参数 | 6 | **静默降级**（见下） |

⇒ 这 16 个里有 11 个是真功能缺口（CSV 导入、导出连接、EXPLAIN、批量执行、
流式查询、保存/删除查询、清空历史），5 个是**刻意不接**（见「预留清单」）。

### 一、最值钱的一条：Tauri v2 的命令参数按 **camelCase** 收，snake_case 会被**静默丢掉**

- 前端传 `access_mode` / `expected_generation` / `max_rows`，
  而 Tauri v2 的宏（`tauri-macros/src/command/wrapper.rs`）把 Rust 参数名转成 camelCase，
  运行时（`tauri/src/ipc/command.rs` 的 `deserialize_option`）**只查 camelCase 的 key**，
  查不到就 `visit_none()` ⇒ **不报错，静默变 None**。
- 后果：`mode = access_mode.unwrap_or("readOnly")` ⇒ **mode 恒为 readOnly**
  ⇒ **写操作永远被只读门禁挡住**；`max_rows` 也永远收不到（界面以为限了，后端没限）。
- **不是读源码猜的，是真跑出来的**：新增 `src-tauri/tests/tauriArgNaming.rs`，
  用 `tauri::test::get_ipc_response` 走**真实 IPC 通道**（mock runtime），4 条断言：
  camelCase 收得到 / snake_case 被静默丢掉 / 两者不能互相替代 / 全 Option 时不报错。
- ⚠ 这条也解释了**为什么这类 bug 能长期活着**：必填参数缺 key 会报错（炸得出来），
  可选参数缺 key **不报错** ⇒ 只有把「两端参数名拉平对比」做成门禁才拦得住。

### 二、「常用查询」是假的：只写进 React state，却弹「已保存到常用查询」

- 改前：`saveAsSavedQuery` 只 `setSavedQueries([...])`，后端的 `save_query` 从没被调用过；
  删除同理，只从内存里删 ⇒ **刷新页面它又回来了**。
- 改后：**先写后端，写成功才更新界面**；写失败就报错，界面保持原样 ——
  宁可让用户重试，也不假装存上了。

### 三、流式查询的「取消」按钮是摆设

- `query_cancel_v2` 查的是 `db::cancel::in_flight()` 这张在途表，
  而 `query_start` **从不往这张表登记** ⇒ 取消永远「查无此单」。
- 而且流式生产者**从不停下来看有没有人叫停** ⇒ 即便登记了，它也会把库一路读完。
- 改法（三处，缺一不可）：
  1. `query_start` 登记进在途表；
  2. 生产者每批问一次 `in_flight().is_cancel_requested()`（新增的廉价查询，不走 `status()`）；
  3. 流结束（跑完 / 出错 / 被取消）都 `finish()` 摘掉，被取消时状态报 `Cancelled`
     **而不是 `Succeeded`** —— 写错了界面就会把一次「用户叫停」显示成一次「跑完了」。
- 回归钉子 2 条：`streaming_query_is_registered_for_cancel`、
  `cancelled_stream_is_not_reported_as_succeeded`。

### 四、批量执行（`execute_batch`）从来没能真正用起来

- 改前：`if mode == "readOnly" { return Err("批量接口当前为只读模式…") }`
  —— **文案与代码自相矛盾**（文案说批量是只读模式，代码却拒的是 readOnly）；
  而可写模式下，同一个 approval 被传给每条语句 ⇒ 第二条必然 `SqlMismatch`
  （审批摘要是一对一的：一条 grant 只对一个 `sql_digest`）。
- 改后：口径明确为**批量 = 一批只读语句**（错误带机器可读码 `READONLY_BLOCKED`）；
  每条语句仍过 `gate_execution` 的只读判据，混进来的写语句当场被挡。
  ⚠ 判据跟着事实走但**强度不许降**：原用例断言的是「批量写必须有审批」，
  现在断言的是「① 可写批量被拒且带码 ② 只读批量里的写语句同样被挡」——**更强，不是更松**；
  另补一条 `execute_batch_runs_readonly_statements` 证明只读批量**真的能跑**。

## 第四阶段续（2026-10-22）：CSV 导入门禁 + 一个跨语言必炸的摘要 bug

上一阶段把 CSV 导入的**界面入口**接上了。但接上之后立刻暴露一件事：
**后端 `csv_import_execute` 原来完全没有任何门禁** ——

```rust
// 改之前的 csv_import_execute（节选）
async fn csv_import_execute(
    config: DBConfig, file_path: String, table_name: String,
    delimiter: Option<String>, limit: Option<usize>, dry_run: Option<bool>,
) -> Result<db::csv_import::ImportResult, String> {
    // ……
    match run_dispatch(&config, &sql).await {   // ← 直接拼 INSERT 写库
```

没有 `access_mode`、没有审批、没有任何校验 ⇒
**把它接进界面 = 新增一条绕过审批的写入后门**（界面上「导入」按钮一点就写库，
审批弹窗根本不会出现）。这属于「先接进来、再补门禁」会踩的典型坑：
**接线和门禁必须同一轮一起做**，否则中间那段时间窗口是敞着的。

### 一、门禁怎么设计的：摘要绑「表 + 行数」

难点在于：**导入的 INSERT 是按文件内容动态拼出来的**，一条审批 grant 绑不住 N 条 INSERT
（`security::evaluate` 核对 `grant.sql_digest == digest_sql(sql)`，摘要是一对一）。

所以摘要不去绑 INSERT 全文，改绑**用户真正要确认的那两件事**：

```
canonical = "CSV_IMPORT table={目标表} rows={真正会写入的行数}"
```

这个设计有三个好处：

1. **语义对**：用户在审批弹窗里点的确实是「往这张表写这么多行」；
2. **覆盖 TOCTOU**：预览之后文件被改过 ⇒ 行数变 ⇒ canonical 变 ⇒ 摘要对不上 ⇒ 拒；
   （行数没变但内容变了也拒不了 —— 这是本方案的**已知边界**，见下面的残留记账）
3. **前端不拼摘要输入**：canonical 由后端 `csv_import_plan` **算好返回**，前端原样拿去算 digest
   ⇒ 两端**结构上**不可能漂移（前端根本没有 `buildCsvImportCanonical` 这个函数）。

三道门（都在 `csv_import_execute` 里）：

| 门 | 触发条件 | 错误码 |
|---|---|---|
| ① 只读通道 | `access_mode != "writable"` | `READONLY_BLOCKED` |
| ② 行数不符 | `expected_rows != 实际解析行数`（文件在预览之后被改过） | `APPROVAL_DENIED` |
| ③ 摘要不符 | 换了表 / 换了文件 / 伪造 grant | `APPROVAL_DENIED` |

### 二、顺带修掉一个**跨语言必炸**的 bug（这个更值钱）

改门禁时必须让两端的摘要一致，一查就查出**原来就对不上**：

| 端 | 长度口径 | 「张」的写法 |
|---|---|---|
| 后端 `security::digest_sql` | `sql.len()` ⇒ **字节数** | 3 |
| 前端 `digestSql` | `sql.length` ⇒ **UTF-16 单元** | 1 |

⇒ **含中文的 SQL，两端摘要必然不同** ⇒ 用户明明在弹窗里点了「授权执行」，
后端却报 `审批 xxx.sql_digest 与请求不匹配` ⇒ **合法写入被误拒**。
更糟的是同一个函数**内部也不自洽**：head 取的是 `chars()`（码点），len 取的是字节。

⚠ 这个 bug **只含中文/emoji 时才发作**，纯 ASCII 时三种口径结果一样 ⇒
只测 ASCII 的用例全绿 ⇒ 很容易被当成"没问题"。这是本轮把黄金向量
**故意塞进非 ASCII 与代理对（emoji）**的原因。

修法：两端统一按 **Unicode 码点数**
（Rust `sql.chars().count()` ↔ TS `Array.from(sql).length`）。
⚠ 注意 Rust 侧**不能**用 `chars().take(64)` 配 `len()` —— 那是码点配字节，同一个函数里两种口径。

两端各钉一份**同样的字面量**（`src-tauri/src/security.rs::digest_golden_vectors`
与 `tests/digestContract.test.ts`）⇒ 改一边必有一边红。

### 三、契约门补上「嵌套结构体」这一层

写门禁时把三个门禁参数打包成了 `ImportGate` 结构体
（`csv_import_execute` 参数从 8 个降到 6 个 —— 8 个会撞 clippy 的 `too_many_arguments` 阈值，
而 clippy 是 CI 的 `-D warnings` 硬门）。打包之后暴露出一个**新的静默降级口子**：

- Tauri v2 的**顶层**命令参数在 JS 侧是 **camelCase**；
- **嵌套结构体字段走 serde**（本仓没有 `rename_all`）⇒ 仍是 **snake_case**。

前端要是把 `access_mode` 写成 `accessMode`，**serde 会静默忽略这个字段**
⇒ `gate.access_mode = None` ⇒ 后端按只读处理 ⇒
用户看到的是「只读模式拒绝 CSV 导入」—— **完全看不出是自己参数名拼错了**。

⇒ `tests/ipcContract.test.ts` 补了**三道嵌套门**：
字段名后端得认 / 必填字段前端得传 / 可选字段要么传要么写明为什么不传。
并用**变异验证**证明这道门咬得住：把前端 `access_mode` 故意改成 `accessMode`
⇒ **2 条用例变红**；改回去 ⇒ 全绿。

### 四、其它一并改掉的

- `csv_preview` → `csv_import_plan`：预览命令顺带产出 canonical，
  「预览」与「审批要绑的东西」因此是同一份产出，不会各算各的。
- 删掉 `dry_run` 参数与它那条分支：它的语义（解析 + 回显）与 `csv_import_plan` 重合，
  而它是一条**不经过门禁的旁路**（能拿到解析结果却不写，风险低但没意义）⇒ 直接删掉。
- `ImportResult.preview` 字段随之删除（`dry_run` 没了，它恒为空）。
- `csv_import.rs` 里行数原来按**原始字节**数（`from_utf8(bytes).unwrap_or("")`）
  ⇒ **GBK 文件解码失败时数出 0 行**，而样本行却是按 GBK 解出来的 ⇒ 两个数对不上。
  现在行数与样本行**来自同一份解码结果**。
- 「原始行数」与「真正会写入的行数」**分成两个字段**（`total_rows` / `import_rows`）：
  文件里可能有空行，空行不生成 INSERT ⇒ 用户点头的必须是**真正会写进去的那个数**。
- 写入走**可写池**（`run_dispatch_mode(..., "writable")`）：原来 `run_dispatch` 固定用只读池，
  等于把写操作挂在一个名为「只读」的池上（对 SQLite/PG 照样能写，但口径就乱了）。

### 残留（如实记账）

1. **行数没变、内容变了，摘要仍会放行** —— canonical 绑的是「表 + 行数」，
   不是文件内容的哈希。所以「预览之后有人把文件第 3 行换掉、行数不变」这种情况
   不会被挡。要挡住得把**内容摘要**也绑进去（可预演：把解析后的每行做一次哈希，
   写进 canonical）—— 本轮没做，因为前端算不出全量内容摘要（预览只给样本行），
   要做就得让后端在 plan 里多返回一个内容摘要字段。
   ⇒ 这是**已知边界，不是隐形缺口**：审批弹窗里展示的是样本行 + 行数，
   用户看得到自己批的是什么。
2. **`csv_import_execute` 的导入是逐行独立 INSERT，没有整单事务** ——
   中途失败会留下**已导入的前几行**（结果里的 `rows_imported` / `rows_failed` 会如实报出来，
   不会假装全成功）。要整单原子得改成事务 + 批量 INSERT，那是独立一轮。
3. **`ssh.rs` 删除后，T-050（SSH 隧道）**仍是未落地项 —— 评估结论留在 05 文档，
   代码不在（理由见上一阶段）。
4. **MySQL/PG 集成测试仍标 `#[ignore]`** —— CI 没有 DB 服务；**标了但没跑过 ≠ 跑过**。
